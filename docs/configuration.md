# Configuration

All optional. Defaults are reasonable for typical use. This file holds the full environment-variable reference (moved from the README) plus the file/directory layout table.

> The **headless runner** (`pi-rukas-headless`) has its own contract documentation in [headless.md](headless.md), which covers the exit-code contract, the `--json` result schema, the NDJSON progress stream, and the `--capabilities` answer. The machine-readable list of every `PI_ENSEMBLE_*` variable the extension reads, with its type, default and scope, is the `inputs` field of `pi-rukas-headless --capabilities` (source: `extension/src/headless/inputs.ts`). A variable this page does not describe is still listed there.

## Paths

| | Path |
|---|---|
| Extension entry | `extension/index.ts` |
| Slash-command bodies | `pi-prompts/*.md` |
| Per-role system prompts (built) | `dist/prompts/standard/<role>.md` (generated by `./install.sh` / `bun run build`; gitignored) |
| Source modules feeding the build | `modules/`, `manifests/`, `agents-base/`, `skill/`, `agents.json` |
| Skills (auto-installed) | `~/.pi/agent/skills/` |
| Run transcripts | `~/.pi/agent/ensemble-runs/<date>/` |
| Saved model config | `~/.pi/agent/ensemble-models.json` |

## Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `PI_ENSEMBLE_QUIET_STATUS` | unset | Set to `1` to disable the **passive** live dispatch deck widget — the below-editor status row per in-flight subagent ([#117](https://github.com/trail-openers/pi-rukas/issues/117)) — and the roster-mode `↓` entry point from an empty editor ([#834](https://github.com/trail-openers/pi-rukas/issues/834)). The **agent list** (`alt+a`), the **live view** ([#839](https://github.com/trail-openers/pi-rukas/issues/839)), and the per-job ring buffer are **not** quiet-gated: the buffer is always created (the `startBuffer` early return that lived here is removed — the gate moved to the widget in `dispatch-deck.ts` `renderNow`), and the agent list opens the live view for a quiet session's rows. Roster mode ([#834](https://github.com/trail-openers/pi-rukas/issues/834)): with the deck enabled (i.e. NOT quiet), `↓` from an EMPTY editor enters it — walk running subagents with `↓`/`↑` (or `j`/`k`), `Enter` opens the **live view** — the child's recent activity (assistant text ≤400 chars, tool calls with ≤240-char args, results ≤200 chars, errors marked) from a per-job 200-event ring buffer, updating as events arrive — with `↑`/`↓`/`PgUp`/`PgDn` to scroll (pauses following), `End` to resume, `s` to open the steer prompt (the view re-opens after), and `Esc` to close; rows without a buffer (lens/adversarial children) open the steer prompt directly instead; finished runs are browsed via `/runs`; exit roster mode with `Esc` or `↑` at the top row; any other key exits and goes to the editor. |
| `PI_ENSEMBLE_QUIET_LIFECYCLE` | unset | Set to `1` to disable scrollback lifecycle markers (`▸ ensemble: dispatched / ✓ finished / ✗ failed`) ([#118](https://github.com/trail-openers/pi-rukas/issues/118)). |
| `PI_ENSEMBLE_SPAWN_TIMEOUT_MS` | `7200000` (2 h) | Runaway backstop per spawned subagent — catches a child looping forever while still emitting output. Liveness (`PI_ENSEMBLE_INACTIVITY_TIMEOUT_MS`) is the real hang detector; this should never fire in normal operation. Operator/CI override — not settable by the agent. |
| `PI_ENSEMBLE_INACTIVITY_TIMEOUT_MS` | `1800000` (30 min) | Kill a child after this long with **zero stdout** while no tool call is in flight. Model-speed-independent, so it is the primary hang detector. `0` disables only the model-silence watch — the tool-inactivity bound is a separate knob. |
| `PI_ENSEMBLE_TOOL_INACTIVITY_TIMEOUT_MS` | `3600000` (60 min) | Kill a child after this long with **zero stdout** while a tool call is in flight (a long bash — a full offline gate, a CI watch — is the normal shape, a wedged tool the bad one). Kill cause `tool-inactivity`. `0` disables only that watch — the model-silence bound is a separate knob. |
| `PI_ENSEMBLE_HANDOFF_CHANNEL` | `forge` | Who reports a handoff. `forge`: the `/work` driver posts the handoff comment and applies `needs-human-attention`. `host`: whatever runs the cycle owns that channel, so the driver posts no handoff comment and applies no `needs-human-attention` label (other cycle comments, such as the review's residual findings, still post); the full handoff body, the typed `cap` and the park reason are in the headless `--json` result (`issues[].handoff`) for the host to deliver. Any other value is `forge`. See [headless.md](headless.md#handoff-channel). |
| `PI_ENSEMBLE_HANDOFF_TIMEOUT_MS` | `480000` (8 min) | How long the `/work` driver waits for the handoff `ops` dispatch — the one that posts the park comment and applies `needs-human-attention`. Its body file is already on disk, so on timeout the driver posts it via in-process `gh` instead; the bound costs nothing but the parsed comment URL. |
| `PI_ENSEMBLE_CYCLE_DEADLINE` | unset | A caller-set deadline for the whole `/work` cycle, as an absolute epoch in **milliseconds** (a value below `1e12` looks like epoch seconds and is ignored, with a trace). It means **"do not start a new step after this point"**: at each step boundary, once `now + PI_ENSEMBLE_HANDOFF_TIMEOUT_MS >= deadline`, the cycle parks with cap `deadline` and posts the handoff (branch, PR, round reached). It is checked at step boundaries only, so a step that started before the deadline runs to completion and **may finish past it** — no step is killed. The driver does not reserve a step's worst case; the host leaves its own margin: set the deadline to your hard kill minus the longest step you can tolerate running past it. Wins over `PI_ENSEMBLE_CYCLE_BUDGET_MS`. Unset = no whole-cycle bound (today's behaviour). |
| `PI_ENSEMBLE_CYCLE_BUDGET_MS` | unset | The same deadline as a duration: resolved to `now + budget` at the first step boundary and persisted in the state file. On a resume the persisted deadline is kept **only while this variable is still set**, so the budget's clock carries across the resume; clear it (and `PI_ENSEMBLE_CYCLE_DEADLINE`) and the resumed cycle has no deadline. Use `--restart` to start a fresh budget. Ignored when `PI_ENSEMBLE_CYCLE_DEADLINE` is set. |
| `PI_ENSEMBLE_ALLOW_DESTRUCTIVE_GIT` | unset | Set to `1` to let subagents run working-tree-discarding git (`checkout` with paths, `restore`, `reset --hard`, `clean -f`). Refused by default at every trust level — a subagent cannot know whether the uncommitted work it would destroy is another workstream's. |
| `PI_ENSEMBLE_SPAWN_CAP` | `64` | Ceiling on concurrent subagent processes. Bounds *local* resources only — provider capacity is rationed by the provider's own 429 + `retry-after`. `0` disables. |
| (no env var) | settings.json `retry.provider.timeoutMs` | `install.sh` writes a 10-min default into `~/.pi/agent/settings.json` (#236, retuned #295). Healthy LLM calls return in seconds; 10 min detects provider hangs fast while leaving headroom for thinking-heavy turns. | |
| (no env var) | settings.json `httpIdleTimeoutMs` (top level) | `install.sh` writes 300000 (5 min, Pi's own default). Controls the undici socket timeout — set as BOTH `headersTimeout` (time-to-first-byte) and `bodyTimeout` (time between streaming chunks). The trade-off: `headersTimeout` ideally wants seconds (a dead socket never sends headers); `bodyTimeout` must tolerate minutes (thinking-heavy generation pauses between chunks). One key drives both — an upstream Pi limitation. Pi reads this key **only at the top level**: before #1347 `install.sh` wrote 120000 under `retry.provider`, where it never applied, so hosts have always run at 300000. `install.sh` removes that nested 120000, and moves any other nested value to the top level. 60000 is recorded as having aborted healthy xhigh-thinking streams; lower it only after re-testing under a thinking-heavy model. Paired with `retry.provider.timeoutMs` (600000 outer SDK deadline); the smaller of the two wins. Edit settings.json directly to tune; `install.sh` uses non-clobbering `//=` so existing values are preserved. |
| (no env var) | settings.json `retry.provider.maxRetries` | `install.sh` writes 3. Without it Pi makes no request-level retry. These retries are silent, so their worst case (4 × (300s idle + 60s `retry-after` ceiling) ≈ 24 min) must fit inside the 30-min model-silence watchdog; 8 would not. Pi's agent-level retry (`retry.maxRetries`, default 3) stacks on top. An existing value is preserved. |
| `PI_ENSEMBLE_INTEGRATION_VERIFY_TIMEOUT_MS` | `900000` (15 min) | Wall-clock for the project's verify command run against the **consolidated** tree, between the commit and the push. This is the first time anything builds the combination of the workstreams — each one passed alone in its own worktree. A failure halts the cycle rather than pushing. A run killed at this bound parks as `verify-timeout:commit-pr` rather than `integration-verify-failed`. |
| `PI_ENSEMBLE_TRANSCRIPT_RETENTION_DAYS` | `5` | Age-based retention for subagent transcripts in `~/.pi/agent/ensemble-runs` — on extension activation, batches whose newest child file is older than this many days are deleted. Fractional values are honoured; unset or an invalid/negative value falls back to `5`. Set to `0` to disable pruning. |
| `PI_ENSEMBLE_DEBUG` | unset | Set to `1` for verbose stderr trace from the extension. |
| `PI_ENSEMBLE_SUBAGENT_MODEL` | unset | Global fallback model for all subagents (see [Configuring subagent models](../README.md#configuring-subagent-models)). |
| `PI_ENSEMBLE_SUBAGENT_PROVIDER` | unset | Optional Pi provider name paired with `PI_ENSEMBLE_SUBAGENT_MODEL` — required for custom OpenAI-compatible providers whose model IDs don't carry a built-in provider prefix (see [custom-providers.md](custom-providers.md)). |
| `PI_ENSEMBLE_MODEL_<ROLE>` | unset | Per-role model override (e.g. `PI_ENSEMBLE_MODEL_DEVELOPER`). Uppercase, `-` → `_`. `<ROLE>` is a spawned role: `DEVELOPER`, `OPS`, `EXPLORE`, `ADVERSARIAL_DEVELOPER` or `CODE_REVIEW_SPECIALIST`; any other name is ignored. `--capabilities` lists them as the family's `members`, as it does for every `<ROLE>`, `<SEAM>` and `<LENS>` family. |
| `PI_ENSEMBLE_PROVIDER_<ROLE>` | unset | Per-role provider override, paired with the corresponding `_MODEL_` var. Same naming rule. |
| `PI_ENSEMBLE_MODEL_LENS_<LENS>` | unset | Per-lens model for one code-review lens child (e.g. `PI_ENSEMBLE_MODEL_LENS_SECURITY`, `PI_ENSEMBLE_MODEL_LENS_ERROR_HANDLING`). `<LENS>` is the lens name `dispatch_lens_review` reports: the `code-review-*` skill directory without the prefix, upper-cased, `-` → `_`. Every lens runs as `code-review-specialist`, so `PI_ENSEMBLE_MODEL_CODE_REVIEW_SPECIALIST` moves all six at once; this spreads them across models. Wins over every role-level choice (`/ensemble-model`, `PI_ENSEMBLE_MODEL_<ROLE>`, `PI_ENSEMBLE_SUBAGENT_MODEL`); a lens without one falls back to that order. Read for lens children only: no other role, and no agent-issued dispatch, can select a lens model. |
| `PI_ENSEMBLE_PROVIDER_LENS_<LENS>` | unset | Per-lens provider, paired with the matching `PI_ENSEMBLE_MODEL_LENS_<LENS>`; ignored on its own. Same naming rule. |
| `PI_ENSEMBLE_LENS_MODEL_CONCURRENCY` | unset | Opt-in bound on how many lens children run at once on one resolved model (provider + model). The rest queue in order and start as a slot frees. For a provider that limits concurrent requests per model and answers six simultaneous lenses with 429 or "no free slot". Lenses on different models never share a slot; the bound is shared by every review in the process. A queued lens leaves the queue as soon as the review is aborted. Unset, `0` or invalid = no bound (all lenses start together). |
| `PI_ENSEMBLE_DISABLE_EXTENSION_FORWARD` | unset | Set to `1` to opt out of auto-forwarding installed extensions to subagents (subagents inherit nothing — disables pi-claude-auth, MCP bridges, etc.). |
| `PI_ENSEMBLE_USER_EXTENSION` | unset | Absolute path or `npm:<pkg>` ref of an extra extension to forward to subagents, on top of the auto-discovered list. |
| `PI_ENSEMBLE_AUTOSAVE` | unset | Set to `1` to opt into a deterministic session summary written to `vipune` on session quit ([#23](https://github.com/trail-openers/pi-rukas/issues/23)). Pure local extract — no LLM call. Off by default. |

**Outcome verification (PR17+):**

| Variable | Default | Purpose |
|---|---|---|
| `PI_ENSEMBLE_VERIFY` | `1` | Set to `0` to disable the driver-side verification gates (diff-existence, verify command). Default ON — catches hollow developer claims pre-commit. |
| `PI_ENSEMBLE_FRONTEND_ONLY_GLOBS` | *(unset)* | **Opt-in (#1013).** Unset or `""` → no skip (full verification always runs). Set to a comma-separated list of extensions to enable the frontend-only skip (suggested: `.css,.html,.svg,.woff,.woff2,.ttf,.otf`). When enabled, if the cumulative union of all worktrees' changed paths is non-empty and every path's extension is in this list, the DERIVED verify chain (package.json typecheck/test, Cargo.toml `cargo check`) is skipped — a CSS-only change must not trigger a backend build. The skip is derived-only: an explicit `.pi/verify-cmd` ALWAYS runs (explicit operator intent beats auto-detection, same philosophy as `PI_ENSEMBLE_VERIFY=0`), and the skip-ratchet / smoke / comment-retention gates are unaffected. Any non-frontend path (or an empty/unreadable diff) runs the full chain — a classification failure never skips a check. Applies to the develop step only; the commit-pr consolidated verify and the `ci` verify-full tier are unaffected. **Coupling:** the skip only takes effect when `verifyCmdFor` has discovered a derived command (Cargo.toml, package.json, go.mod, or pyproject.toml at the repo root). Projects whose build tool is not in that list have no derived command to skip — add a `.pi/verify-cmd` to enable explicit verify (which always runs regardless of the skip gate). |
| `PI_ENSEMBLE_VERIFY_CONCURRENCY` | *(host budget)* | Ceiling on verify, smoke and full-verify commands the driver runs at once, across every cycle in the process; excess queues FIFO. Unset: one per two CPUs and per 2 GiB of memory (after any cgroup limit), at least 1: 8 on a 16-CPU / 64 GiB host, 4 on 8 CPUs / 16 GiB, 1 (serial) on 2-3 CPUs. Verify runs were unbounded before this setting existed, so a smaller host now queues them. `0` removes the bound and restores the old behaviour. The host budget and the limits a cycle chose are traced at cycle start (`PI_ENSEMBLE_DEBUG=1`) and reported as `resources` by `pi-rukas-headless --json` and `--capabilities`. |
| `PI_ENSEMBLE_VERIFY_TIMEOUT_MS` | `600000` (10 min) | Timeout for both verify command and smoke command. Shared timeout keeps gate configuration simple. Override for slow commands or fast CI. When `.pi/verify-cmd-fast` exists, the two tiers share this bound: the full command gets what the fast one left. A develop verify run killed at the bound parks as `verify-timeout:develop`, not `verify-failed:develop`. The run reached no verdict about the code, and the handoff says so and names the bound. |
| (no env var) | `.pi/verify-cmd-fast` | **Opt-in (#1324).** The first non-empty, non-comment line is a cheap check, such as typecheck plus lint (`bunx tsc --noEmit && bun run check`). It runs before the verify command everywhere the driver runs it: each worktree, the consolidated tree at develop and at commit-pr, and the baseline probe. A fast failure skips the full run, so a type error shows up in seconds rather than after the whole suite. The develop prompt tells each developer to run only this tier and leave the full command to the driver, so M parallel workstreams no longer run M full suites at once. Absent → only the verify command runs, as before. |
| `PI_ENSEMBLE_VERIFY_FULL` | `1` | Set to `0` to skip the verify-full tier. When `.pi/verify-cmd-full` exists, its first non-empty non-comment line runs at the `ci` step **before** the CI watch, in the group's worktree. There is deliberately no derivation fallback — an inferred "full suite" recreates the ambiguity the tier removes. Absent file → `verify-full-status: skipped`, visibly. |
| `PI_ENSEMBLE_VERIFY_FULL_TIMEOUT_MS` | `1800000` (30 min) | Timeout for the verify-full command. Separate from the fast-tier timeout because a full suite is expected to be slow. |
| `PI_ENSEMBLE_VERIFY_TEST_JOBS` | `2` | **Offline smoke runner (#1365).** Concurrent jobs in `extension/smoke-tests/lib/verify-loop.sh`'s bounded pool. Accepted only as `1`-`99`; anything else warns and uses `2`. The value is then clamped down to the number of collected tests and to `16` (each job is a full `bun` process, so past that the pool competes with itself), and either clamp prints a warning. `1` is strictly sequential — the pre-#1365 shape, same output and exit codes. Output is replayed in argument order, so the digest does not depend on finish order. Read once at startup. See [troubleshooting](troubleshooting.md) → pool symptoms. |
| `PI_ENSEMBLE_VERIFY_TEST_TIMEOUT_S` | `300` | **Offline smoke runner (#1014).** Per-test watchdog, in seconds. Accepted only as a positive integer; anything else warns and uses `300`. A test that hits the bound is reported `FAILED: <file> (timed out after <N>s)` with a `✗ timed out after <N>s` line prepended to its capture, and its whole descendant tree is killed (SIGTERM, then SIGKILL for survivors), so a hung test does not take the pool with it. Read once at startup. |
| (no env var) | `.pi/dirty-root-exempt` | **Opt-in (#1362).** One repo-relative prefix per line; `#` comments and blank lines ignored; `./` stripped, trailing `/` normalised. Paths under one of its prefixes are **not repo-root dirt** and are **never staged at repoRoot**, so a tool's own local file (`.claude/settings.local.json`) no longer blocks a cycle at the branch step, preflight, consolidated verify, integrate or a restore claim. Ships with no entries — an absent file means the empty list and unchanged behaviour. Enforced: **untracked (`??`) only** (a tracked modification, deletion or rename under an exempt prefix is still dirt); prefix matching honours a `/` boundary (`.claude` never exempts `.claudefoo/x`); **protected paths cannot be exempted** (an entry naming `.github/`, `.pi/`, `CODEOWNERS` or `agents.json` is rejected with a trace); absolute / `..` / glob / empty entries are rejected with a trace. **Repo root only** — a workstream worktree stages its output exactly as before, so a deliverable inside an exempt prefix is still committed. Read once per cycle before the branch step; `.pi/` being protected means a develop patch cannot widen it mid-cycle. An unreadable file yields the empty list **plus a trace and a handoff record** — a broken config never blocks an otherwise-clean cycle, and if the cycle then blocks on repo-root residue the handoff names the failed read beside the paths (they were all judged against an empty list). A file the **cycle itself** wrote under an exempt prefix is still stashed and recoverable — the list decides what is dirt, not what is the cycle's work. See [troubleshooting](troubleshooting.md) → "/work refuses on a dirty repo root caused by a tool's own local files". |
| `PI_ENSEMBLE_WIDENING_SCAN` | `1` | Set to `0` to disable the deterministic type-widening scan. When on, the diff is scanned for removed compiler-enforced invariants (`T` → `Option<T>`, added `\| null`, removed `readonly`/`assert`/`pub`/`mut`, narrowing to `any`) and findings are routed into the lens context for the ARCHITECTURE lens. **Route-only** — it never fails a cycle. |
| `PI_ENSEMBLE_SKIP_RATCHET` | `1` | Set to `0` to disable the skip-marker ratchet (prevents net additions of `#[ignore]`, `it.skip`, etc.). Default ON — a skipped test is a disabled gate. |
| `VIPUNE_PROJECT` | *(git auto-detect)* | Forwarded to every specialist child when set, so memory is scoped explicitly rather than inferred from whatever directory the child happens to run in. |
| `PI_ENSEMBLE_CLAIM_SCAN` | `1` | Set to `0` to disable the claim scan — a deterministic, model-free check that every checkable particular a diff adds to a **prose** file (a quantity, product model, version, path, flag, env var or URL) occurs somewhere in the repository **outside the prose asserting it**. Findings are reported as `CLAIM_SCAN` at MEDIUM. Catches invented specifications; see [troubleshooting](troubleshooting.md) → "False claims in a diff". |
| `PI_ENSEMBLE_LENS_EVIDENCE` | `1` | Set to `0` to stop supplying reviewers with the post-change content of changed prose files. Default ON — lens children run in a worktree checked out at the **base** commit, so a file they open shows the code as it was, and a claim contradicting something outside the diff is otherwise invisible to them. |
| `PI_ENSEMBLE_REVIEW_THRESHOLD` | *(unset)* | Blocking severity for review findings — `CRITICAL`, `HIGH`, `MEDIUM` or `LOW`. Overrides whatever the project's `AGENTS.md` says. Unset, the project decides; absent any statement, the default is `MEDIUM`. `CRITICAL` findings block regardless. |
| `PI_ENSEMBLE_POLICY_JUDGE` | `1` | Set to `0` to disable the natural-language policy judge. Default ON — merge authority is resolved by a short-lived read-only child that reads the project's `AGENTS.md`/`CLAUDE.md` and answers one question through a schema-validated tool call, and whose answer is honoured only if the sentence it quotes actually appears in the file. Disabling it does **not** fall back to guessing: the gate simply denies, so merging then requires `/work N --merge`. See [troubleshooting](troubleshooting.md) → "Merge authority". |
| `PI_ENSEMBLE_DECISIONS` | `1` | Set to `0` to make every decision seam rule-only (no classifier, no LLM call), except the grandfathered policy judge, which only `PI_ENSEMBLE_POLICY_JUDGE` governs. Every `decide()` call, including one that abstains or errors, still writes exactly one decision-log record — every driver call site supplies the repo root; a caller that supplies none gets the record traced instead (`.pi/work-state/<lowest issue>/decisions.jsonl` inside a `/work` cycle, `.pi/decisions.jsonl` otherwise, always under the main checkout, secrets redacted). |
| `PI_ENSEMBLE_DECISION_MODEL` | *(unset)* | `provider/id` of a Pi classifier model (e.g. `typesafe/jev-latest`) for the decision seams to try first. Unset, the seams use the session's default LLM, then the deterministic rule. pi-rukas works fully with neither. |
| `PI_ENSEMBLE_DECISION_MODE_<SEAM>` | *(registry: `shadow`)* | Per-seam mode: `off` (rule only), `shadow` (model consulted and logged, rule answer used) or `enforce` (model answer combined with the rule by the seam's composition policy). `<SEAM>` is the seam id upper-cased with `-` → `_`: `FAILURE_CAUSE` (`failure-cause`, a dispatch failure's root cause, asked only where the rule is not exact). It is shadow-only today: fired without awaiting, so `enforce` is refused for it (traced) rather than acted on. In `shadow` it sends the model (the session LLM, or the `PI_ENSEMBLE_DECISION_MODEL` classifier, which may be a different provider) the failure's provider message and the last 600 characters of the subagent's output, after secret redaction; set the mode to `off` to keep that text on the host. Ignored by the grandfathered policy judge (`POLICY_JUDGE`). |
| `PI_ENSEMBLE_DECISION_TIMEOUT_MS_<SEAM>` | *(registry)* | Per-seam timeout per model backend, in ms. A backend past it abstains and the next one is tried. |
| `PI_ENSEMBLE_DECISION_BUDGET_<SEAM>` | *(registry)* | Per-seam token budget. A state estimated over it is abstained before any call (never truncated) and a response whose usage exceeds it abstains; the reason is logged. |
| `PI_ENSEMBLE_PROTECTED_PATHS` | `1` | Set to `0` to allow a cycle to write to the files that define its own gates (`.github/`, `.pi/`, `CODEOWNERS`, `agents.json`). Default ON — the develop gate halts and names the paths, because a cycle that edits its own CI workflow is grading its own work. To allow specific paths for one cycle instead, pass `/work N --allow-protected <path>` (operator-only, single issue; exact paths, repeatable or comma-separated). Policy prose (`AGENTS.md`, `CLAUDE.md`) is **not** halted; it is neutralised instead, by reading merge authority at the cycle's base commit. See [troubleshooting](troubleshooting.md) → "A cycle cannot grant itself authority". |
| `PI_ENSEMBLE_SMOKE` | `1` | Set to `0` to disable the product smoke command gate (runs `.pi/smoke-cmd` if present). Default ON — tests passing in isolation doesn't prove the product works. |
| `PI_ENSEMBLE_PR_PREFLIGHT` | `1` | Set to `0` to skip the branch-step check for an open PR already covering the issue. Default ON — `--restart` wipes the driver's state file but not GitHub, and without this the driver rebuilds the issue and opens a duplicate (#358 was orphaned by #359 exactly this way). |
| `PI_ENSEMBLE_PARALLEL_GROUPS` | `3` | How many issue groups `/work N M P …` runs concurrently. Unset, the default is lowered on a small host so that groups × `PI_ENSEMBLE_MAX_WORKSTREAMS` fits the host's workstream slots (two per CPU or one per GiB of memory, whichever is lower, after any cgroup CPU quota or memory limit); it is never raised. The default of 3 holds only from about 9 CPUs and 18 GiB up: an 8-CPU / 16 GiB host runs 2, a 4-CPU or 8 GiB host 1. An explicit value (including `3`) wins over the host budget. Child-process load is bounded by `PI_ENSEMBLE_SPAWN_CAP` and verify load by `PI_ENSEMBLE_VERIFY_CONCURRENCY`, not by this number. |
| `PI_ENSEMBLE_PARALLEL_WORK` | `1` | Set to `0` to force strictly sequential group execution regardless of `PI_ENSEMBLE_PARALLEL_GROUPS`. |
| `PI_ENSEMBLE_SPECULATIVE_EXPLORE` | *(unset)* | Set to `1` to run a speculative `explore` child alongside each developer during `develop`. Off by default: it passes its findings through a scratch file the developer reads 3-7s into its run and writes 14-130s later, so every measured access returned `ENOENT` — 397k-956k tokens per child that nothing consumed — and `develop` resolves at `max(developer, speculative)`, so it finished last on 6 of 23 measured branches. |
| `PI_ENSEMBLE_MAX_WORKSTREAMS` | `6` | Ceiling on workstreams per cycle. Excess folds into the last workstream (paths unioned, fold recorded) rather than being dropped. Each workstream is a worktree and a developer child, so this bounds fanout.. Unset, it is also lowered to the host's workstream slots on a host with fewer than 3 CPUs or 6 GiB; an explicit value wins. |
| `PI_ENSEMBLE_PLAN_CACHE_TTL_MS` | `7200000` (2 h) | How long a `start_plan_driver` dry run stays confirmable: a confirm echoing its `reviewedDigest` inside this window (same descriptor, context, type and origin/<default> commit) files the reviewed spec verbatim. `0` disables the expiry (an operator answering hours later from a phone). A value that is not a non-negative integer is ignored. After expiry the confirm re-runs the pipeline and, if the spec it drafts differs from the reviewed one, files nothing and asks again. |
| `PI_ENSEMBLE_PLAN_CACHE_DIR` | *(unset: `<git common dir>/pi-plan-cache`)* | Absolute directory for the `start_plan_driver` dry-run cache, for a launcher that makes a fresh clone per turn. Created if missing. Entries go in a per-repository subdirectory keyed on the `origin` URL (or the clone's git dir when there is no origin), so clones of one repository share it and different repositories do not collide. A relative path is ignored. |

## Skills and review lenses

The six-pass code review fans out one `code-review-specialist` child per lens, each pinned to its own `code-review-*` skill. The lens roster is **data, not code**: it is parsed from the `code-review-*` SKILL.md files in the installed skills dir, with each lens's ordering declared in that skill's frontmatter.

### Where the skills live

- `PI_ENSEMBLE_SKILLS_DIR` overrides the skills directory the extension reads from; unset, it defaults to `~/.pi/agent/skills` (`piSkillsDir()` in `extension/src/lens-review.ts`).
- `./install.sh` populates it: it symlinks every directory under the repo's `skill/` into `$PI_AGENT_DIR/skills` (via `ln -sfn`; `$PI_AGENT_DIR` defaults to `~/.pi/agent` — see the Paths table, which lists the default `~/.pi/agent/skills/`). Re-run `./install.sh` after adding a lens so the new symlink lands in the installed dir.
- Installed entries are symlinks, and every check below `stat`s them through the symlink — a dangling symlink counts as missing.

### Pre-spawn verification

Before any lens child is spawned, the extension verifies the skills dir and the roster:

- **Expected lenses** = the roster of the **bundled** repo `skill/` dir (`BUNDLED_SKILL_DIR` / `buildExpectedRoster` in `extension/src/lens-roster.ts`).
- A lens that is **missing or dangling** in the installed dir (present in the bundled roster but not stat-able at the installed path) is blocked with `skill not installed: <absolute installed path> (not spawned)` and zero attempts — the review degrades to `REVIEW_INCOMPLETE` instead of silently becoming a five-pass `APPROVED`.
- A **missing, empty, or no-`code-review-*`-skill** dir (a `code-review-*` plain file does not count — only directories do) blocks **all** lenses with the single message `skills dir <path> missing or empty — run ./install.sh` (`skillsDirUsable` in `extension/src/lens-review-skills.ts`), one blocked row per bundled lens, no spawns at all.
- **Extra** `code-review-*` lenses present only in the installed dir (not in the bundled roster) are allowed — a seventh lens is a configuration change, not a code change.
- A lens that **is** installed but fails to parse (SKILL.md unreadable, no frontmatter `name:`, `name:` ≠ directory, `precedence:` missing/not an integer/not a safe integer, or duplicate `precedence:` — which blocks **both** lenses and names both) shows its parse error as a blocked row.

A per-lens `statSync` of `<skills dir>/<skill>` immediately before spawning repeats the missing-skill check as executed evidence (`extension/src/lens-review-child.ts`), blocking that lens with the same `skill not installed: <path> (not spawned)` message without burning a spawn.

### Skill Load Status marker

Each lens child self-reports its skill load in its closing reply: `Skill Load Status: [SUCCESS/FAILED]` (the format in `agents-base/code-review-specialist.md`), and the parent parses it (`readEnumMarker`).

- `FAILED` **blocks that lens** — the verdict can never be `APPROVED` (`REVIEW_INCOMPLETE`), while the lens's findings are **kept** (a failed skill load doesn't invalidate evidence the child already gathered). The block's reason reads `skill load reported FAILED by the child (<skill>)`.
- An **absent or unknown** marker does **not** block: the pre-spawn `stat` above is the executed evidence the skill existed, so an unexercised honor system is only traced (`PI_ENSEMBLE_DEBUG=1`), never a verdict input.

### Adding a review lens

1. Create `skill/code-review-<name>/SKILL.md` whose first frontmatter block has `name: code-review-<name>` (the frontmatter `name:` must equal the directory name) and a **unique integer** `precedence:` (lower runs first). The shipped lenses use `precedence` 10–60: `code-review-security` 10, `code-review-error-handling` 20, `code-review-type-safety` 30, `code-review-performance` 40, `code-review-architecture` 50, `code-review-simplicity` 60.
2. The lens name is derived from the directory: strip the `code-review-` prefix, replace `-` with `_`, uppercase (`code-review-error-handling` → `ERROR_HANDLING`).
3. Add the lens to **both** prose lists: the launch list in `agents-base/project-manager.md` (a `@code-review-specialist (lens: <NAME>, skill: code-review-<name>)` line) and the lens mapping in `agents-base/code-review-specialist.md` — the prose gate fails if either list diverges from the roster.
4. Run `./install.sh` to symlink the new skill into the installed skills dir.
5. No TypeScript change is required.

### What the gates enforce

Offline smoke tests (part of the pre-push gate) enforce the wiring contract:

- **`test-skill-name-surface.ts`** — skill-name surface: every skill name referenced in the prompt sources (`agents-base/`, `modules/`, `pi-prompts/`) resolves to `skill/<name>/SKILL.md`, every SKILL.md's first-frontmatter `name:` equals its directory name, and every roster lens resolves.
- **`test-lens-roster.ts`** — roster resolution from SKILL.md frontmatter (a 7th lens is discovered with no code change), `precedence:` present / a safe integer / unique (a duplicate blocks both lenses and names both), a missing skill or broken entry blocks that lens with a named error, and a fixture with only 5 of the 6 bundled lenses yields 6 rows with the missing one blocked — never a silently reduced or reordered roster.
- **`test-lens-roster-expected.ts`** — installed-set semantics of `buildExpectedRoster`: a missing or dangling bundled lens produces the `skill not installed: … (not spawned)` row; a lens installed but blocked by its own parse error appears once with that error (no duplicate `not installed` row on top); a non-safe-integer `precedence:` blocks with a named error.
- **`test-lens-skill-wiring.ts`** — the pre-spawn checks against the real `runLensReview` with a mocked spawner: one missing lens blocks only that lens with its absolute path and zero spawns for it; a missing/empty/unrelated-only skills dir blocks all lenses with the install message and zero spawns total; a dangling symlink blocks that lens; a `Skill Load Status: FAILED` reply blocks that lens (findings kept) while an absent marker leaves the review `APPROVED`-eligible. `test-lens-skill-plain-file.ts` pins that a `code-review-*` plain **file** (not a directory) yields the all-blocked install message, matching the roster predicate.
- **Prose-list gate** (`test-lens-roster.ts`, case g) — every roster lens (name **and** skill) appears in both the `project-manager.md` launch list and the `code-review-specialist.md` lens list, and the PM launch list contains no lens the roster doesn't have.
- **Failure direction (bogus fixtures)** — each gate above is proven to fail: the tests build deliberate fixtures (a phantom skill reference, a frontmatter `name:` ≠ directory, a divergent prose list, a broken skill) and assert the failure is reported; a gate that cannot fail is worthless. The repo-side check then asserts the real tree is clean.


`PI_ENSEMBLE_ROLE` is set internally by `spawn.ts` for subagent processes; do not set it manually.
