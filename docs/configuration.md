# Configuration

All optional. Defaults are reasonable for typical use. This file holds the full environment-variable reference (moved from the README) plus the file/directory layout table.

> The **headless runner** (`pi-rukas-headless`) has its own contract documentation in [headless.md](headless.md), which covers the exit-code contract, the `--json` result schema, the NDJSON progress stream, and the `--capabilities` answer. The machine-readable list of every `PI_ENSEMBLE_*` variable the extension reads, with its type, default and scope, is the `inputs` field of `pi-rukas-headless --capabilities` (source: `extension/src/headless/inputs.ts`). A variable this page does not describe is still listed there.

## Paths

| | Path |
|---|---|
| Extension entry | `extension/index.ts` |
| Slash-command bodies | `pi-prompts/*.md` |
| Per-role system prompts (built) | `dist/prompts/standard/<role>.md` (generated by `./install.sh` / `bun run build`; gitignored) |
| Source modules feeding the build | `modules/`, `manifests/`, `agents-base/`, `skill/`, `agents.json` |
| Skills (auto-installed) | `~/.pi/agent/skills/` |
| Run transcripts | `~/.pi/agent/ensemble-runs/<date>/` |
| Saved model config | `~/.pi/agent/ensemble-models.json` |
| Private backlog (optional) | `<repository root>/.backlog/backlog.md` — a separate clone, kept out of `git status` by a per-clone `.git/info/exclude` entry |
| Merge-author allowlist | `.pi/merge-authors` — **opt-in per repository**: absent means the repository has no author gate at all (every other gate is unchanged); present, it lists one login per line, matched case-insensitively, and is read at the cycle's base commit by the merge-author gate (#2181). A file that is present and unreadable, a symlink, a directory or empty after comments refuses every merge. |

## Private backlog (optional)

If you keep your real priority order somewhere other than the issue tracker, clone that repository into the project at `.backlog/` and maintain a `backlog.md` inside it:

```bash
git clone <your-private-backlog-url> .backlog
grep -qx '/.backlog/' .git/info/exclude || echo '/.backlog/' >> .git/info/exclude
```

**Exclude it per clone, never in a committed `.gitignore`.** The directory is a nested clone holding private content, and the ignore rule is about *this* checkout's hygiene, not the project's shape — the same reasoning as the harness's own per-clone entries (`work-driver-git-exclude.ts`). A committed `/.backlog/` line would ship your working arrangement to every clone of the repository, including ones whose operators have no such backlog.

**The path is the repository root, not the directory you launched `pi` from.** The reminder resolves the toplevel by walking up from the session directory to the first directory holding a `.git` (a directory in a normal clone, a file in a linked worktree; bounded at 50 levels), so a session started inside `extension/` or any other subdirectory still finds `<toplevel>/.backlog`. Cloning the backlog anywhere other than the repository root means nothing sees it.

**What the reminder does.** When `.backlog/backlog.md` exists, the PM session is handed one short paragraph telling it the backlog exists, where it is, that its `## Now (in order)` list is the agreed order, that the order changes only with your explicit approval and by committing to that repository (never by editing the file uncommitted), and that machine-filed issues sit under Triage until you promote them. That is all it does: it is a pointer, not a reader. Nothing here fetches the backlog, runs git against it, or puts its content into a prompt.

**It fires only for a real clone.** `.backlog` itself must be a real directory (not a symlink to somewhere else in the tree), must contain a `.git` marker, and `backlog.md` must be a regular file. A directory someone committed called `.backlog`, a `.backlog` that is a symlink, and a `backlog.md` that is a symlink or a directory, get no reminder — the feature is about your private clone, and telling the PM to treat whatever a symlink points at as the agreed order is not that.

**What happens without it: nothing.** No `.backlog/`, a `.backlog/` that is not a clone, no `backlog.md`, a `backlog.md` that is a symlink or a directory, or a session with no directory at all all produce a session prompt byte-identical to a pi-rukas without this feature — there is no flag to turn on and no setting to set. The `.backlog` check runs per PM turn, so an operator who clones the backlog mid-session is heard on the next turn. Two bounds keep it cheap: a 250 ms wall clock bounds the *wait*, so a hung mount cannot hold a turn open, and one outstanding probe per process bounds the *requests*, so a mount that never answers costs one hanging probe rather than one per turn. (The repository root itself is remembered per session directory — the walk up a fixed path is the part that cannot change.) An ordinary absence (`ENOENT`/`ENOTDIR`) is silent; a real fault on your own clone (`EACCES`, `EIO`) prints one `WARN` line per code and path and is otherwise treated the same way as absence: the paragraph is simply not added, and nothing throws. The check runs only in the PM session — subagent prompts (developer, explore, ops, reviewers) never gain the paragraph. Set `PI_ENSEMBLE_BACKLOG_REMINDER=0` to switch the probe off entirely.

Rendering the backlog itself — a panel at `/start`, so you see the agreed order rather than only being told one exists — is the follow-on half of this feature and is not in this release.

## Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `PI_ENSEMBLE_BACKLOG_REMINDER` | `1` | Set to `0` to stop the PM's private-backlog reminder ([#1730](https://github.com/trail-openers/pi-rukas/issues/1730)). With the default, each PM turn probes the **repository root**'s `.backlog/` — it must be a real directory (not a symlink) holding a `.git` marker and a regular-file `backlog.md`, not a symlink — and appends one paragraph pointing the PM at it. `0` skips the probe entirely: no filesystem read, no paragraph. See [Private backlog](#private-backlog-optional). |
| `PI_ENSEMBLE_QUIET_STATUS` | unset | Set to `1` to disable the **passive** live dispatch deck widget — the below-editor status row per in-flight subagent ([#117](https://github.com/trail-openers/pi-rukas/issues/117)) — and the roster-mode `↓` entry point from an empty editor ([#834](https://github.com/trail-openers/pi-rukas/issues/834)). The **agent list** (`alt+a`), the **live view** ([#839](https://github.com/trail-openers/pi-rukas/issues/839)), and the per-job ring buffer are **not** quiet-gated: the buffer is always created (the `startBuffer` early return that lived here is removed — the gate moved to the widget in `dispatch-deck.ts` `renderNow`), and the agent list opens the live view for a quiet session's rows. Roster mode ([#834](https://github.com/trail-openers/pi-rukas/issues/834)): with the deck enabled (i.e. NOT quiet), `↓` from an EMPTY editor enters it — walk running subagents with `↓`/`↑` (or `j`/`k`), `Enter` opens the **live view** — the child's recent activity (assistant text ≤400 chars, tool calls with ≤240-char args, results ≤200 chars, errors marked) from a per-job 200-event ring buffer, updating as events arrive — with `↑`/`↓`/`PgUp`/`PgDn` to scroll (pauses following), `End` to resume, `s` to open the steer prompt (the view re-opens after), and `Esc` to close; rows without a buffer (lens/adversarial children) open the steer prompt directly instead; finished runs are browsed via `/runs`; exit roster mode with `Esc` or `↑` at the top row; any other key exits and goes to the editor. |
| `PI_ENSEMBLE_QUIET_LIFECYCLE` | unset | Set to `1` to disable scrollback lifecycle markers (`▸ ensemble: dispatched / ✓ finished / ✗ failed`) ([#118](https://github.com/trail-openers/pi-rukas/issues/118)). |
| `PI_ENSEMBLE_SPAWN_TIMEOUT_MS` | `7200000` (2 h) | Runaway backstop per spawned subagent — catches a child looping forever while still emitting output. Liveness (`PI_ENSEMBLE_INACTIVITY_TIMEOUT_MS`) is the real hang detector; this should never fire in normal operation. Operator/CI override — not settable by the agent. |
| `PI_ENSEMBLE_INACTIVITY_TIMEOUT_MS` | `1800000` (30 min) | Kill a child after this long with **zero stdout** while no tool call is in flight. Model-speed-independent, so it is the primary hang detector. `0` disables only the model-silence watch — the tool-inactivity bound is a separate knob. |
| `PI_ENSEMBLE_TOOL_INACTIVITY_TIMEOUT_MS` | `3600000` (60 min) | Kill a child after this long with **zero stdout** while a tool call is in flight (a long bash — a full offline gate, a CI watch — is the normal shape, a wedged tool the bad one). Kill cause `tool-inactivity`. `0` disables only that watch — the model-silence bound is a separate knob. Also derives the developer's own suite bound: the develop / lens-fix prompts tell the child to wrap each test command in `timeout N` where N is **a third of this value**, clamped to 1–1200 s (1200 s at the default; a value the parser cannot read falls back to the same 1200 s, never `timeout NaN`). Shrink this knob and the suite bound shrinks with it — the prompt can never tell a child to run longer than the watchdog that would take it down. |
| `PI_ENSEMBLE_PROGRESS_SILENCE_MS` | `0` (off) | Opt-in: end a child that keeps emitting but makes **no progress** for this long — no tool result, no streamed tool output with new bytes, no `report_finding`, no turn whose last text or tool call differs from the one before. Token growth, steers, stdin echoes, call starts and a repeated identical turn do not count, and a child that has emitted nothing is measured from its spawn. Kill cause `no-progress`, classified `self-killed:no-progress` and not retried. A set value is floored at 30 min with no tool call in flight and 60 min while one is (the stdout-silence defaults above), because Pi emits nothing mid-turn or inside a silent tool. It never lengthens any other bound: a progressing child still ends at its per-child bound or a lean step's `minutes`. `0` or unset leaves every child exactly as before. Source: `child-progress.ts`. |
| `PI_ENSEMBLE_HANDOFF_CHANNEL` | `forge` | Who reports a handoff. `forge`: the `/work` driver posts the handoff comment and applies `needs-human-attention`. `host`: whatever runs the cycle owns that channel, so the driver posts no handoff comment and applies no `needs-human-attention` label (other cycle comments, such as the review's residual findings, still post); the full handoff body, the typed `cap` and the park reason are in the headless `--json` result (`issues[].handoff`) for the host to deliver. Any other value is `forge`. See [headless.md](headless.md#handoff-channel). |
| `PI_ENSEMBLE_HANDOFF_TIMEOUT_MS` | `480000` (8 min) | How long the `/work` driver waits for the handoff `ops` dispatch — the one that posts the park comment and applies `needs-human-attention`. Its body file is already on disk, so on timeout the driver posts it via in-process `gh` instead; the bound costs nothing but the parsed comment URL. With `PI_ENSEMBLE_CYCLE_DEADLINE` set it is also the **handoff allowance**: the time after the deadline the caller leaves for the handoff before its hard kill. A handoff that starts late is bounded by what is left of the allowance, less up to a minute kept back for the in-process `gh` fallback ([#1593](https://github.com/trail-openers/pi-rukas/issues/1593)). |
| `PI_ENSEMBLE_CYCLE_DEADLINE` | unset | A caller-set deadline for the whole `/work` cycle, as an absolute epoch in **milliseconds** (a value below `1e12` looks like epoch seconds and is ignored, with a trace). It is **where step work ends**; only the handoff runs after it. Set it to your hard kill minus your handoff allowance, and pass that allowance as `PI_ENSEMBLE_HANDOFF_TIMEOUT_MS` — the handoff then has the allowance to itself and lands before the kill. At each step boundary, once `now + PI_ENSEMBLE_HANDOFF_TIMEOUT_MS >= deadline`, the cycle starts no new step: it parks with cap `deadline` and posts the handoff (branch, PR, round reached). A step already running when the deadline arrives does not run on: every child the cycle spawns is bounded by what the deadline leaves (its errorTail then reads `killed … at the caller's cycle deadline`), and a step that ends past the deadline records `deadline` as the cycle's cap after its own verdict, which the cap's evidence names. Before [#1593](https://github.com/trail-openers/pi-rukas/issues/1593) such a step ran to its own backstop (2 h for a developer), into the host's kill, and its last verdict stood as the cycle's cap. The driver's own non-dispatch gates (the verify command, `PI_ENSEMBLE_VERIFY_TIMEOUT_MS`) are not clamped and may still run briefly past the deadline, inside the allowance. Wins over `PI_ENSEMBLE_CYCLE_BUDGET_MS`. Unset = no whole-cycle bound (today's behaviour). |
| `PI_ENSEMBLE_CYCLE_BUDGET_MS` | unset | The same deadline as a duration: resolved to `now + budget` at the first step boundary and persisted in the state file. On a resume the persisted deadline is kept **only while this variable is still set**, so the budget's clock carries across the resume; clear it (and `PI_ENSEMBLE_CYCLE_DEADLINE`) and the resumed cycle has no deadline. Use `--restart` to start a fresh budget. Ignored when `PI_ENSEMBLE_CYCLE_DEADLINE` is set. On `pi-rukas-headless work-lean` an explicit `--timeout` outranks it while `PI_ENSEMBLE_TIMEOUT_FLAG_PRECEDENCE` is on (its shipped default) — see its row below. |
| `PI_ENSEMBLE_REVIEW_WALL_CLOCK_MS` | `5400000` (90 min) | The `/work` **review-loop wall clock** — how long the fix loop (lens-review → developer-fix → adversarial → re-review) may run before the driver caps it. This is the ceiling the **driver enforces**: it bounds the `lens-fix` dispatch and the adversarial fix pass to what remains **minus the owed lens round's reserve** (`MIN_USEFUL_MS["lens-review"]`, 10 min — #1742: a fixer may not spend the budget its own re-review needs), refuses to start a fixer once what remains is under `PI_ENSEMBLE_HANDOFF_TIMEOUT_MS` + 60 s, and past the ceiling parks with the `lens-review-timeout` cap-hit (named `wall-clock` before result schema v4, #1384). It is also the number every surface prints — the footer's `cap 12m/90m`, `cap …/90m` denominator, `/work-status`'s `wall-clock x/y`, and the handoff comment — all of which previously hardcoded 90 and ignored any other value. Read per call, so it applies mid-cycle. **Clamped:** values must be a whole number of milliseconds at or above `600000` (10 min); anything else (zero, negative, fractional, non-numeric, or below the floor) is rejected with a trace naming the value and the 90-minute default is used — a ceiling under the handoff grace would leave no window in which a fixer can be armed, so a typo disables the bound rather than tightening it. Independent of `PI_ENSEMBLE_REVIEW_ENFORCE`, which *removes* enforcement entirely (`0` = the number is shown and never acted on); this variable only changes **what** the ceiling is, never **whether** it applies. Distinct from `PI_ENSEMBLE_REVIEW_CAP_MS`. Source: `review-budget.ts`. |
| `PI_ENSEMBLE_LENS_FIX_BOUND_MS` | `2700000` (45 min) | The **caller ceiling on one `lens-fix` dispatch** (#1742). Measured: a lens-fix ran ~152 minutes of a 90-minute loop — the wall clock bounds what a fixer may START with, but the fixer's own child bound (30 min + grace) is the only per-dispatch ceiling it carried, so one long fixer could consume the whole loop budget and starve the round that owes a re-check of its own fix. This knob caps the dispatch itself: the armed `timeoutMs` is the minimum of `PI_ENSEMBLE_REVIEW_WALL_CLOCK_MS` remaining minus the owed round's reserve and this ceiling — each only ever shortens the other. Same per-call read and the same 10-minute floor and reject-and-trace rule as the other review knobs. With `PI_ENSEMBLE_REVIEW_ENFORCE=0` no bound is armed at all (the opt-out is byte-identical). Source: `review-budget.ts`. |
| `PI_ENSEMBLE_ADVERSARIAL_BOUND_MS` | `1800000` (30 min) | The **adversarial reviewer's own per-child run bound** ([#1827](https://github.com/trail-openers/pi-rukas/issues/1827)). The generic child bound never reached it: `runAdversarialLoop` spawns the reviewer with no `childBoundMs`, so the only ceilings on one review round were the 2-hour backstop, the inactivity watchdogs and the loop detector — all of which watch for *silence or repetition*, and a reviewer that keeps making distinct tool calls is neither. Measured: a reviewer emitted `VERDICT: APPROVED`, then made 476 more turns and ~80M tokens with no cap firing. This knob gives that child the bound a lens child already carries: a wrap-up steer at the bound, a kill `PI_ENSEMBLE_CHILD_BOUND_GRACE_MS` later, cause `child-bound`. It applies to the **reviewer** only — the fix-pass `developer` the same loop spawns is untouched, as it has always been bounded by its own develop dispatch. Read per call; a value the parser cannot read, zero, or a negative falls back to the 30-minute default rather than unbounding the child. Values above **4 hours** are clamped to it, with a trace: past the 2-hour spawn backstop a child could never live long enough to reach a larger bound, so the clamp keeps the knob honest rather than promising a ceiling that cannot fire. The advisory steers (slow notice, turn nudge, the child-bound wrap-up) stand down for this child once any killing bound has armed. Source: `review-bounds.ts`. |
| `PI_ENSEMBLE_EXPLORE_REASK_BOUND_MS` | `180000` (3 min) | The **wall clock on the one same-session follow-up an explore reply gets** ([#2611](https://github.com/trail-openers/pi-rukas/issues/2611)). An explore child that ends its turn on a status line — it says it is about to write the spec and emits no `INTENT-VERDICT:` line and no `## Spec` — is asked ONCE, in its own session, for the two artefacts its reply contract already promised, before the step pays for a fresh child that repeats the whole investigation. This is that ask's bound. A child the bound kills still answers with whatever reply it printed before the kill (the strict `## Spec` reader decides whether it counts); only a child that printed nothing fails as a timeout. Read per call. Zero, a negative or a value the parser cannot read falls back to this default rather than unbounding the ask or killing it the instant it starts. A value too low for a reply to land costs the ask and nothing else: the step proceeds to the fresh re-dispatch it would have paid for anyway, and the cap evidence names the abandoned ask. Source: `work-driver-explore-reask.ts`. |
| `PI_ENSEMBLE_ADVERSARIAL_VERDICT_REASK` | `1` | **Re-ask a round whose reviewer fenced its whole report.** The candidate reader (`adversarial-verdict-read.ts`) refuses a `VERDICT:` line inside a code fence by design — a fenced verdict is one being shown, not signed — so a reviewer that copied its role prompt's `## Output Format` layout verbatim produced no readable verdict and the round was recorded as an infrastructure failure over a review that was actually performed. On (any value but `0`), such a round gets ONE re-ask: a short child resumed on the reviewer's OWN session file (`pi --mode rpc --session <transcript>`, the `reattachChild` precedent) is given one prompt that names NO verdict value, and its answer is read by the same strict `parseVerdict` — a fenced answer, a menu echo or no answer at all stays unreadable and lands on the same infrastructure failure as before. The child carries the reviewer's role, system prompt, model and tool fence (so it cannot write), runs in the **reviewed tree** rather than the driver's working directory, and carries its own 5-minute bound; the round keeps the ORIGINAL reviewer's transcript, model and kill cause, and only the re-ask's tokens join the totals. The operator sees where the verdict came from: a trace line, a lifecycle line tagged `adversarial-verdict-reask`, and the clause "verdict obtained on re-ask" in the result. At most one re-ask per round number. `0` turns both halves off — the reviewer's brief loses the placement instruction and the loop never spawns the second child, byte for byte as before. Read at call time. Sources: `adversarial-verdict-reask.ts`, `adversarial-prompts.ts`, `adversarial.ts`. |
| `PI_ENSEMBLE_REVIEW_SKILL_READS` | `3` | **How many times a reviewer child may open its OWN skill file before the run is steered and then ended** ([#1827](https://github.com/trail-openers/pi-rukas/issues/1827)). Observed shape: a lens child re-reads its `SKILL.md` for hundreds of turns, **alternating** `read`, `cat` and `grep` — which is exactly why no existing cap saw it. The loop detector keys on tool+args, so a `read` and a `bash` are different fingerprints and none ever repeats; `ChildProgress` keys on the command string, and `cat X` / `grep Y X` differ. Neither the slow-run notice nor a PM steer stops a child that is busy. With N = this value: N or fewer reads do nothing (a healthy reviewer loads its skill once, maybe re-checks a table); the (N+1)-th read steers **once**, naming the file (the steer is **advisory** — it does not stand the other supervision seams down, because it often works); the (N+2)-th ends the child with kill cause `review-skill-reread`. The knob accepts a **positive integer**: an empty or unset value is the default, and `0`, a fraction or garbage is traced by name and falls back to `3` (reading an empty knob as `0` would have made the first read of every review a violation); anything above `50` is clamped to `50`, with a trace. Two rules keep it from ending a child for doing its job: only reads of the **driver-supplied skill path's `SKILL.md`** count (another skill's file, the skill directory, or a sibling reference doc never advance the counter), and only genuine **reads** do — `grep`/`rg` name a path without opening it, so they are not counted, while `read`, `cat` and `head` are, through the same predicate the skill-load proof already owns (its candidates are computed once per child, not per stdout line). In practice this bounds **lens children**: the cap counts only a driver-supplied skill path, the lens dispatch always supplies one, and the adversarial reviewer's is usually absent — so that child carries no counter at all rather than an unlimited one. The kill is suppressed only while the child's **process has exited** — there is nothing left to stop (the seam is the shared `childHasExited`, spawn-support.ts, also read by the caps stack and the per-child bound). An intermediate `agent_end` — the prompt's own end, which Pi emits at every in-process retry boundary — does **not** suppress it (#1847): that flag describes one segment of a review while the process behind it is still running and still opening its skill file, which is exactly when the cap has work left to do. The advisory **steer** does stand down on both an exited child and a child that has reported, since a lecture written at a stdin that is gone reaches nobody. **A re-read kill keeps the child's evidence** — findings and closing summary stand and the lane is not marked `not reviewed` — because a child that opened its skill N+1 times demonstrably had it and did the review it managed to do. If another cause already named the child's end when the cap reaches its kill, both causes are traced and the earlier one stands. Source: `review-bounds.ts` and `review-bounds-nested.ts` (the nested shape). |
| `PI_ENSEMBLE_DEVELOPER_BASH_TIMEOUT_MS` | `900000` (15 min) | The **wall-clock bound on one bash call of a developer child** ([#2377](https://github.com/trail-openers/pi-rukas/issues/2377)) — the developer twin of `PI_ENSEMBLE_REVIEW_BASH_TIMEOUT_MS`, same mechanism, its own default. Measured on lean `specify`: one developer bash call that never returned sat 41 minutes until the step bound killed the step. The same `tool_call` hook in the mode-independent child guard list lowers the call's `timeout` (Pi's own bash-tool parameter, in seconds) to this bound; Pi's bash enforces it and answers the child with `Command timed out after N seconds`, the child keeps its turn and still reports. **Nothing is killed** — no kill cause, no parent timer, no process kill; the tool result is the record that it fired (`PI_ENSEMBLE_DEBUG=1` adds the hook's trace). A timeout the model chose for itself and is **smaller** than the bound is kept. Applies to the `developer` role only — the lean `specify`/`build`/`challenge`/`fix` seats and the `/work` develop and lens-fix developers all run under that role — and to nested calls a codemode script makes; `ops`, `explore` and the parent PM session are never bounded. A call that genuinely needs longer is the child's to **split or background** with its own `timeout` — and the effective ceiling on one call is the **smaller** of this bound and whatever `timeout` wrapper the child typed, which by default sits **above** it (the developer prompt's suite wrapper is `timeout 1200`), so a full offline suite is run in shards or backgrounded with its own `timeout`. Sitting below the lean `specify` step budget (20 min) is the point: a call that never returns ends the call rather than the step. Inert under `PI_ENSEMBLE_DISPATCH_CAPS=0`. The value is a **whole number of milliseconds from 1000 up to the largest whose rounded seconds still fit Pi's bash ceiling** (written seconds × 1000 at most `2147483000`); unset or empty is the `900000` default and **`0` is the operator's opt-out** — no bound and no warning, byte-identical to the pre-#2377 behaviour; anything else (a fraction, negative, `1e308`, past the ceiling, garbage) warns by name and means **no bound** — never `NaN`. Neither knob bounds the other role's calls. Read per call. Source: `review-bash-timeout.ts`. |
| `PI_ENSEMBLE_REVIEW_BASH_TIMEOUT_MS` | `600000` (10 min) | The **wall-clock bound on one bash call of a reviewer child** ([#2140](https://github.com/trail-openers/pi-rukas/issues/2140)). A tool call that never returns also never yields the turn, so no steer can land and the whole-child bound ends the review with no verdict. A timeout the model chose for itself and is **smaller** than the bound is kept. Applies to `code-review-specialist` and `adversarial-developer` only, and to nested calls a codemode script makes (the codemode call itself is not a bash call). Read per call. Source: `review-bash-timeout.ts`. |
| `PI_ENSEMBLE_REVIEW_CAP_MS` | `5400000` (90 min) | The ceiling the **`check_review_cap` tool** answers against — the Step 7 fix-loop cap an agent queries itself, which returns `{ok: false}` and the prose `cap is N minutes` past it. Kept a **separate variable** from `PI_ENSEMBLE_REVIEW_WALL_CLOCK_MS` on purpose: that one is a kill inside the driver, this one is an advisory answer an agent acts on, and merging them would mean tuning the tool's prose silently changes when the driver kills a child. | `PI_ENSEMBLE_LENS_FIX_LAND_AHEAD` | `1` | **The escape hatch for the lens-fix partial-fix conversion.** Set to `0` to restore the pre-#1779 shape: a `lens-fix` killed at its own bound is a plain dispatch failure that HALTs with `step-failed:lens-fix` and routes to handoff — even when the fixer had already committed, stranding those commits in a worktree nobody reads. The default converts that kill into a completed dispatch **after** keeping its `dispatch-failed` record (the failure stays in the log with its exit code and error tail; the appended completion is the event the router reads), and then moves the lens worktree onto the landed commit — detached, bounded, inside the lens tree only — so the next round's reposition gate sees `already-at-tip` instead of a tree holding commits the branch lacks. Single-issue cycles only. `/plan` reads the same manifests. See [Sandbox](sandbox.md#an-issues-images-in-work). |

## Skills and review lenses

The six-pass code review fans out one `code-review-specialist` child per lens, each pinned to its own `code-review-*` skill. The lens roster is **data, not code**: it is parsed from the `code-review-*` SKILL.md files in the installed skills dir, with each lens's ordering declared in that skill's frontmatter.

### Where the skills live

- `PI_ENSEMBLE_SKILLS_DIR` overrides the skills directory the extension reads from; unset, it defaults to `~/.pi/agent/skills` (`piSkillsDir()` in `extension/src/lens-review.ts`).
- `./install.sh` populates it: it symlinks every directory under the repo's `skill/` into `$PI_AGENT_DIR/skills` (via `ln -sfn`; `$PI_AGENT_DIR` defaults to `~/.pi/agent` — see the Paths table, which lists the default `~/.pi/agent/skills/`). Re-run `./install.sh` after adding a lens so the new symlink lands in the installed dir.
- Installed entries are symlinks, and every check below `stat`s them through the symlink — a dangling symlink counts as missing.

### Pre-spawn verification

Before any lens child is spawned, the extension verifies the skills dir and the roster:

- **Expected lenses** = the roster of the **bundled** repo `skill/` dir (`BUNDLED_SKILL_DIR` / `buildExpectedRoster` in `extension/src/lens-roster.ts`).
- A lens that is **missing or dangling** in the installed dir (present in the bundled roster but not stat-able at the installed path) is blocked with `skill not installed: <absolute installed path> (not spawned)` and zero attempts — the review degrades to `REVIEW_INCOMPLETE` instead of silently becoming a five-pass `APPROVED`.
- A **missing, empty, or no-`code-review-*`-skill** dir (a `code-review-*` plain file does not count — only directories do) blocks **all** lenses with the single message `skills dir <path> missing or empty — run ./install.sh` (`skillsDirUsable` in `extension/src/lens-review-skills.ts`), one blocked row per bundled lens, no spawns at all.
- **Extra** `code-review-*` lenses present only in the installed dir (not in the bundled roster) are allowed — a seventh lens is a configuration change, not a code change.
- A lens that **is** installed but fails to parse (SKILL.md unreadable, no frontmatter `name:`, `name:` ≠ directory, `precedence:` missing/not an integer/not a safe integer, or duplicate `precedence:` — which blocks **both** lenses and names both) shows its parse error as a blocked row.

A per-lens `statSync` of `<skills dir>/<skill>` immediately before spawning repeats the missing-skill check as executed evidence (`extension/src/lens-review-child.ts`), blocking that lens with the same `skill not installed: <path> (not spawned)` message without burning a spawn.

### Skill delivery (was: the Skill Load Status marker)

**#1847 replaced this whole contract for lens children.** The parent reads
`<skills dir>/<skill>/SKILL.md` itself, strips the frontmatter
(`firstFrontmatterBlock`) and injects the body into the lens prompt inside
`<lens-skill-body nonce="…">…</lens-skill-body>`. The nonce is a fresh UUID per
read and the tag name carries it, because every bundled lens skill contains
triple-backtick fences — a fence-based wrapper is escapable by the very content
it wraps — and a body that contains the closing tag is **refused** rather than
inlined. An unreadable or missing body blocks that lens **before** the spawn
with `skill not readable: <path> (not spawned)`, the same shape as
`skill not installed:` above.

`--skill` is dropped from the lens argv (`--no-skills` stays). It only ever
**advertised** name, description and location — `formatSkillsForPrompt` never
inlines a body (only the `/skill:name` slash command does, which no pi-rukas
path calls) — so the advertised location was the thing that manufactured the
reload: every lens went to open the file it had been told where to find. With
the body in the prompt there is nothing left to advertise, and
`agents-base/code-review-specialist.md` no longer makes loading a skill a
mandatory first action or asks a lens for a `Skill Loaded:` / `Skill Load
Status:` line.

What replaces the self-report is the driver's own record: the lens row carries
`skillDelivered`, and `lens-review-render.ts` appends it to that lens's row as
` — skill delivered inline (<skill dir>)` after the finding count (so a clean
lane reads `0 findings — skill delivered inline (code-review-security)`). The
name in it is the skill directory, passed through `neutraliseEvidence` like
every other agent-adjacent field on the line, because a lens row is quoted into
PR comments. There is no child claim left to corroborate, so the #1530
`skillLoadProof` shadow check is **retired for lens children** — a lens that
never called `read` is the expected outcome, and neither the SHADOW warn nor a
`FAILED` block can fire on a marker nothing reads. The proof itself
(`lens-skill-load-proof.ts`) stays and is still exercised: it is the predicate
the re-read cap counts with.

**A stale `Skill Load Status:` in a lens reply is inert.** It blocks nothing and
warns nothing (`test-lens-skill-load-consumer.ts` pins the retirement). Only the
parent-side read gates a lens now.

### Adding a review lens

1. Create `skill/code-review-<name>/SKILL.md` whose first frontmatter block has `name: code-review-<name>` (the frontmatter `name:` must equal the directory name) and a **unique integer** `precedence:` (lower runs first). The shipped lenses use `precedence` 10–60: `code-review-security` 10, `code-review-error-handling` 20, `code-review-type-safety` 30, `code-review-performance` 40, `code-review-architecture` 50, `code-review-simplicity` 60.
2. The lens name is derived from the directory: strip the `code-review-` prefix, replace `-` with `_`, uppercase (`code-review-error-handling` → `ERROR_HANDLING`).
3. Add the lens to **both** prose lists: the launch list in `agents-base/project-manager.md` (a `@code-review-specialist (lens: <NAME>, skill: code-review-<name>)` line) and the lens mapping in `agents-base/code-review-specialist.md` — the prose gate fails if either list diverges from the roster.
4. Run `./install.sh` to symlink the new skill into the installed skills dir.
5. No TypeScript change is required.

### What the gates enforce

Offline smoke tests (part of the pre-push gate) enforce the wiring contract:

- **`test-skill-name-surface.ts`** — skill-name surface: every skill name referenced in the prompt sources (`agents-base/`, `modules/`, `pi-prompts/`) resolves to `skill/<name>/SKILL.md`, every SKILL.md's first-frontmatter `name:` equals its directory name, and every roster lens resolves.
- **`test-lens-roster.ts`** — roster resolution from SKILL.md frontmatter (a 7th lens is discovered with no code change), `precedence:` present / a safe integer / unique (a duplicate blocks both lenses and names both), a missing skill or broken entry blocks that lens with a named error, and a fixture with only 5 of the 6 bundled lenses yields 6 rows with the missing one blocked — never a silently reduced or reordered roster.
- **`test-lens-roster-expected.ts`** — installed-set semantics of `buildExpectedRoster`: a missing or dangling bundled lens produces the `skill not installed: … (not spawned)` row; a lens installed but blocked by its own parse error appears once with that error (no duplicate `not installed` row on top); a non-safe-integer `precedence:` blocks with a named error.
- **`test-lens-skill-load-verified.ts` / `-round2` / `-round3`** — the pure `skillLoadProof` shapes: which tools and which path spellings count, the `unproven` / `unverifiable` split, the containment rule that rejects a `SKILL.md` outside the skill dir, and that a writing segment — a redirect target or `sed -i` — is not a read. These exercise the predicate the re-read cap counts with; they no longer run through a lens child, because #1847 retired the lens-side proof.
- **`test-lens-skill-load-consumer.ts`** — the **retirement**, pinned in the consumer that used to enforce the old contract: no SHADOW warn is produced on any shape (a `SUCCESS` with no read, an out-of-tree `SKILL.md`, a redirect, an in-place `sed`, a prefix-sharing path, a sibling file), a stale `Skill Load Status: FAILED` blocks nothing, and the lens's findings stand regardless. `test-lens-prompt-skill-path-1847.ts` pins the path-safety wall that predates #1847 and now also refuses to print the skill path at all.
- **`test-lens-skill-inline-1847.ts`** — the parent-side read: the body is delivered with its frontmatter stripped, an unreadable body blocks pre-spawn with `skill not readable: <path> (not spawned)` while the roster still parses the same entry, the wrapper holds against a payload of backtick fences, a body containing the closing tag is refused without echoing its content, the nonce is per-read, and all six bundled skills read and wrap.
- **`test-lens-skill-wiring.ts`** — the pre-spawn checks against the real `runLensReview` with a mocked spawner: one missing lens blocks only that lens with its absolute path and zero spawns for it; a missing/empty/unrelated-only skills dir blocks all lenses with the install message and zero spawns total; a dangling symlink blocks that lens. `test-lens-skill-plain-file.ts` pins that a `code-review-*` plain **file** (not a directory) yields the all-blocked install message, matching the roster predicate.
- **`test-lens-skill-argv-1847.ts`** — the lens argv and the delivery record, both asserted on every recorded spawn: the argv carries `--no-skills` and neither `--skill` nor `--skill=`, still loads the lens-reporter extension, and is exactly the three flags it should be; the row's `skillDelivered` names the skill directory and renders as the ` — skill delivered inline (<skill dir>)` suffix the docs above describe (placed after the finding count, and neutralised so a marker-bearing dir name cannot hand the report its own verdict). A blocked row records no delivery.
- **`test-review-skill-reread-1847.ts`** — the two counting/liveness holes #1847 closes: nested codemode reads (`tool_execution_start` with `parentToolCallId`) count for both `read`-with-`path` and `bash`-with-`command`; the parent `codemode` block does not; a top-level start, another skill's file, a non-reader and a malformed `args` never advance the counter; and an intermediate `agent_end` does not disarm the kill while an exited child is never killed or steered again.
- **Prose-list gate** (`test-lens-roster.ts`, case g) — every roster lens (name **and** skill) appears in both the `project-manager.md` launch list and the `code-review-specialist.md` lens list, and the PM launch list contains no lens the roster doesn't have.
- **Failure direction (bogus fixtures)** — each gate above is proven to fail: the tests build deliberate fixtures (a phantom skill reference, a frontmatter `name:` ≠ directory, a divergent prose list, a broken skill) and assert the failure is reported; a gate that cannot fail is worthless. The repo-side check then asserts the real tree is clean.


`PI_ENSEMBLE_ROLE` is set internally by `spawn.ts` for subagent processes; do not set it manually.
