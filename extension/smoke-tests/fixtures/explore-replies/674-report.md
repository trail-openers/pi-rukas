## Spec

### Intent
Make the /work driver's handoff/park path (a) consolidate workstream worktree commits onto the feature branch before printing recovery instructions (or, when consolidation is infeasible, print per-worktree paths + HEAD SHAs + working cherry-pick commands instead of the provably-empty main-checkout commands), (b) stop accumulating worktrees across terminal cycles, and (c) retry the in-process forge handoff post (comment + label) with backoff before the "HANDOFF DISPATCH INCOMPLETE" banner.

### Deliverables

[paths: extension/src/work-driver-handoff.ts, extension/src/work-driver-integrate.ts, extension/src/work-driver-cherry-pick.ts, extension/src/workflow-state-schema.ts]

Both .chat.ts and .md.ts else-blocks are replaced together; no handoff surface ever prints the generic git status/add -p/push -u origin block in that shape. [paths: extension/src/work-driver-handoff-recovery.ts, extension/src/work-driver-handoff-recovery.chat.ts, extension/src/work-driver-handoff-recovery.md.ts, extension/src/work-driver-handoff-message.ts]

### Acceptance criteria
- A state file with status=handoff, cap=verify-failed:develop, branchName set, and a non-empty pipelineState.worktrees map renders recovery blocks on BOTH surfaces that name each actual .worktrees/issue-N-<id> path + its detached HEAD SHA + a working cherry-pick command, or state that the branch contains the work — and contain NO git -C <repoRoot> status / diff --stat / add -p / push -u origin <branch> lines.
- Handoff on a develop-parked cycle leaves the feature branch containing the workstream work (git rev-list --count baseSha..<branch> > 0) when consolidation is feasible; on cherry-pick conflict it degrades to the per-worktree fallback and the handoff still completes.
- The in-chat "Worktree state" section reports committed work correctly (not "0 file(s) modified" for clean-tree-with-commits worktrees).
- A forge whose issueComment fails once then succeeds yields a handoff-emitted with commentUrl + labelApplied:true and NO "HANDOFF DISPATCH INCOMPLETE" banner; a permanently-failing forge exhausts retries and then shows the banner with verbatim manual gh commands.
- After a terminal handoff/aborted/merged cycle, the cycle's own .worktrees/issue-N-* worktrees are removed (consolidated or accurately reported); a subsequent /work on the same issue's branch step no longer hits DirtyWorktreeError on that cycle's leftover worktrees.
- Pre-branch caps (intent-park, explore-*) with no worktrees/branch keep their current byte-for-byte fallback (test-handoff-tells-the-truth.ts pins keep passing).

### Assumptions
- Handoff-time consolidation SKIPS the verifyCmd gate — the work already failed verify at develop, re-running it is redundant and would block the preferred path; if the implementer wants to verify the consolidated branch, a verify failure during handoff consolidation must route to the accurate-worktree-paths fallback, never block the handoff. — The issue's own gap-gate [MEDIUM] flags this ambiguity; skipping is the defensible default because handoff is terminal and the operator can re-verify on takeover.
- integrate() is NOT modified to add a no-push option; the handoff consolidation calls orchestrateCherryPick directly (or extracts the non-push portion) so it does NOT push — pushing a not-yet-reviewed, verify-failed branch to origin on handoff is not what the operator needs. — The issue reference explicitly says "integrate() PUSHES, so a handoff consolidation needs a no-push variant" and the gap-gate softens that to "must not push; implementer may add an option, extract, or call orchestrateCherryPick directly".
- Terminal-exit cleanup removes ONLY worktrees keyed in pipelineState.worktrees (never on-disk .worktrees/issue-<N>-* orphans not in the state file, never sibling live cycles' worktrees). — The issue's own edge-case list says "must only delete the cycle's own worktrees keyed in pipelineState.worktrees"; the orphan-dir sweep is exactly what runWorktreeSweep at cycle launch already handles, and expanding scope here would collide with the out-of-scope list.
- The forge-post retry is NOT crash-safe: a crash mid-retry is covered by the existing priorHandoffCommentUrl dedupe (resume sees no commentUrl on the prior handoff-emitted and re-posts; the retry itself is best-effort within the single runHandoff call). — The issue's own edge case says "safe today"; making it crash-safe would require new event-log fields for no benefit the issue asks for.
- The forge-post retry is a small fixed backoff (2 attempts total, bounded wait, PI_ENSEMBLE_HANDOFF_POST_RETRY=0 escape hatch) rather than a provider-stated-delay classifier. — The forge is a local gh/glab CLI, not a rate-limited LLM provider; dispatch-retry.ts's retryDecision shape is the model for boundedness, not the delay source.

## Workstreams

Two workstreams. Items 1+2 (worktree consolidation + recovery + cleanup) and item 3 (forge-post retry) are cleanly separable with disjoint primary touchpoints, but they share work-driver-handoff.ts (the runHandoff file) — d1/d3/d4 land in the pre-render window, d5 in the forge-fallback block of the same file. That shared file means parallel developers would both be editing work-driver-handoff.ts and could collide; the issue itself says "scope this as ONE ticket if items 1+2+3 share enough implementation surface ... split into 2 if investigation shows ... cleanly separable with no shared touch points". They are NOT cleanly separable — both touch work-driver-handoff.ts — so per the issue's own scoping rule this stays ONE ticket, but it is large enough that the PLAN step should decompose it into workstreams that partition work-driver-handoff.ts ownership:

- task-a (worktree side, the large one): d1 + d2 + d3 + d4 + their tests. Owns the pre-render window of work-driver-handoff.ts (captureWorktreeSnapshot, runWorktreeTeardown call site, new consolidation call), work-driver-handoff-recovery.ts/.chat.ts/.md.ts, work-driver-handoff-message.ts "Worktree state" section, workflow-state-schema.ts handoffSnapshot fields, work-driver-worktree-sweep.ts terminal cleanup, work-driver-integrate.ts / work-driver-cherry-pick.ts reuse (read-only), and test-handoff-rendering.ts / test-handoff-tells-the-truth.ts / test-work-driver-worktree-sweep.ts.
- task-b (forge-post retry, small): d5 + its test. Owns ONLY the in-process forge fallback block in work-driver-handoff.ts (the if (!commentUrl || !labelApplied) section) plus a new test-handoff-post-retry.ts (or extension of test-work-driver-handoff-forge-fallback.ts). The plan must put work-driver-handoff.ts in task-b's in-scope list with the comment that task-b touches only the forge-fallback block, and task-a's out-of-scope must explicitly exclude the forge-fallback block — OR the plan runs task-b first and task-a second sequentially against the same file. The safer decomposition: sequential single-developer cycles (task-b is ~30 lines + 1 test; task-a is the rest). If the plan insists on parallel workstreams, task-b must NOT own work-driver-handoff.ts and instead the retry logic must be extracted to a new module (e.g. work-driver-handoff-forge.ts) that task-b owns and task-a imports — but that extraction is itself a change to work-driver-handoff.ts, so the cleanest plan is sequential: task-b (forge retry, with the small extraction if desired) → task-a (worktree consolidation + recovery + cleanup).
- Out-of-scope for both: work-driver-verify-develop.ts, worktree-provision.ts, work-driver-branch-salvage.ts, worktree.ts, runWorktreeSweep (launch-time), handoffDispatchTimeoutMs / test-handoff-bounded.ts, the adversarial gate, the develop-step commit doctrine.
